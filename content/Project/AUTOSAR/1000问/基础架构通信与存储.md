# AUTOSAR 1000问：基础架构、通信与存储

本篇整理 Flomo 中已形成完整答案的首批 10 个基础问题。内容围绕 AUTOSAR 的标准定位、分层、RTE、Runnable、配置生成、通信路由和非易失存储展开。原始题目库仍保留在 Flomo，本文是迁移后的结构化答案。

## 一、基础概念

### Q1. 什么是 AUTOSAR？全称和核心含义是什么？

**答案：** AUTOSAR 是 *AUTomotive Open System Architecture*（汽车开放系统架构）。它不是一个可直接安装运行的软件，也不是某个供应商的工具，而是一组面向汽车电子软件的标准、架构约定、接口规范和方法论。

它主要解决三类问题：

- **软硬件解耦**：应用软件通过标准接口访问基础软件，减少对具体 MCU 和驱动实现的依赖。
- **软件组件复用**：SW-C 按端口、接口和行为描述组织，便于跨 ECU 或车型复用。
- **供应链协作**：OEM、Tier 1、软件供应商和工具供应商可以围绕 ARXML、接口定义和标准模块协作。

Classic Platform 面向资源受限 MCU 上的确定性控制；Adaptive Platform 面向高性能计算平台和 POSIX 操作系统环境。两者目标相近，但运行模型、通信方式和执行管理机制并不相同。

**工程理解：** AUTOSAR 更像汽车软件的“共同接口合同”。它降低跨团队协作成本，但不会自动保证系统设计正确；配置、集成、时序分析和验证仍然必不可少。

### Q2. AUTOSAR 联盟成立于哪一年？最初由哪些公司发起？

**答案：** AUTOSAR 联盟于 **2003 年**成立。最初的六家 Core Partners 是 BMW、Bosch、Continental、DaimlerChrysler、Siemens VDO 和 Volkswagen，覆盖整车厂与一级供应商。

成立背景是汽车 ECU 数量和软件复杂度持续上升，各项目重复开发基础软件、接口和集成方案，造成高昂维护成本。OEM 提供整车需求和平台约束，Tier 1 提供 ECU 与系统实现经验，联合制定标准更容易形成可落地的生态。

**边界说明：** 后续成员加入和组织治理结构会随时间变化；“最初六家”不能与当前全部成员名单混为一谈。正式历史材料应以 AUTOSAR 官方组织介绍为准。

## 二、基础架构

### Q3. AUTOSAR 分层架构各层通过什么接口通信？谁依赖谁？

**答案：** Classic Platform 常见的纵向结构是 Application / RTE / BSW / MCAL / Microcontroller。应用 SW-C 通过 RTE 访问其他 SW-C 或 BSW 服务；BSW 内部通过模块接口协作；MCAL 通过微控制器抽象接口访问芯片外设。

- **Application / SW-C**：承载业务逻辑，使用 Port、Interface、Runnable、Sender-Receiver 或 Client-Server 等建模元素。
- **RTE**：根据系统描述和 ECU 配置生成通信与调用代码，隔离应用与部署细节。
- **BSW**：包含服务层、ECU 抽象层、复杂驱动等，提供通信、诊断、存储、系统服务。
- **MCAL**：封装 MCU 外设访问，如 Can、Dio、Adc、Pwm、Mcu、Fls。
- **硬件**：控制器、寄存器、中断和物理外设。

应用逻辑的依赖方向总体朝向抽象服务，但实际 BSW 并非简单的单向“瀑布层”：模块间存在标准规定的回调、接口和依赖关系，不能把所有模块都理解为只调用下一层。

~~~~mermaid
flowchart TB
  SWC[应用层：SW-C / Runnable]
  RTE[RTE：生成的应用运行时接口]
  BSW[BSW：服务层 / ECU抽象层 / 驱动接口]
  MCAL[MCAL：Can / Dio / Adc / Pwm / Fls]
  HW[MCU 外设与寄存器]
  SWC <--> RTE
  RTE <--> BSW
  BSW <--> MCAL
  MCAL <--> HW
~~~~

### Q4. RTE 解决什么核心问题？没有 RTE 会怎样？

**答案：** RTE（Run-Time Environment）把 SW-C 的逻辑接口映射为 ECU 上可执行的通信与调用机制。应用只依赖端口和接口，不必在业务代码中硬编码数据究竟位于本核、另一核还是远端 ECU。

RTE 主要屏蔽：

1. **通信部署差异**：同 ECU 内部通信、跨核通信、跨 ECU 通信可由配置和生成结果实现。
2. **接口调用细节**：生成 Rte_Read、Rte_Write、Rte_Call 等接口。
3. **Runnable 触发映射**：把 TimingEvent、DataReceivedEvent、OperationInvokedEvent 等映射到任务或事件触发机制。

没有 RTE，SW-C 就需要自己处理通信、同步、调度和平台差异，应用代码会与 ECU 部署结构、通信协议和 OS 细节紧耦合。

**调试提示：** 不要只看 Rte_Read 的函数名就断定数据路径。应结合生成代码、RTE 配置、端口映射、Runnable 事件和 ECU 部署信息确认实际实现。

### Q5. SW-C 在运行时如何调度？它与普通 C 函数有什么区别？

**答案：** SW-C 是软件组件的建模与封装单元，通常包含一个或多个 Runnable。Runnable 在实现层面往往对应 C 函数，但调用时机由 RTE/OS 的配置与触发机制决定。

- 周期触发：TimingEvent 映射到周期任务或调度表。
- 数据触发：DataReceivedEvent 在数据到达或满足配置条件时触发。
- 操作触发：OperationInvokedEvent 对应 Client-Server 操作调用。
- 其他触发：还可能有初始化、模式切换等事件，具体取决于平台版本和配置模型。

普通 C 函数通常由代码中的调用语句显式调用；Runnable 的触发关系更多由模型、RTE 生成代码和 OS 配置共同决定。因此排查 Runnable 未执行时，除了检查函数本身，还要检查事件、映射、任务激活和 OS 调度。

~~~~mermaid
flowchart TD
  E1[TimingEvent] --> R[RTE 事件映射]
  E2[DataReceivedEvent] --> R
  E3[OperationInvokedEvent] --> R
  R --> T[OS Task / 调用上下文]
  T --> C[Runnable C 函数]
  C --> D[Rte_Read / Rte_Write / Rte_Call]
~~~~

### Q6. 为什么把配置和代码生成拆成两个步骤？

**答案：** 配置描述系统“需要什么”，代码生成把配置转成特定 ECU、工具链和软件版本下的实现。

- 配置资产：ARXML、模块参数、端口连接、调度映射、通信路由等。
- 生成产物：RTE、BSW 配置代码、头文件、链接与集成所需的辅助文件。
- 分离的价值：配置可审查、可追溯、可复用；生成代码可重复生成、比较和验证。

**工程实践：** ARXML 和生成工具版本应纳入版本控制与构建记录；生成代码是否提交仓库，应遵循项目基线策略。不能笼统断言“生成代码永远不进版本库”，因为不同 OEM/Tier 供应链有不同交付要求。

## 三、通信栈

### Q7. CAN 通信从 PDU 到总线经过 COM → PduR → CanIf → Can，各层做什么？

**答案：**

- **COM**：处理 I-PDU 内的 Signal 打包/解包、信号更新、发送模式和超时等信号层语义。
- **PduR**：依据配置转发 I-PDU，在通信、诊断和网关路径间路由。
- **CanIf**：提供总线无关的 CAN 接口抽象，管理 CAN ID、硬件对象、控制器状态和 Tx/Rx 回调映射。
- **Can Driver**：面向具体 CAN 控制器，负责驱动硬件发送、接收和中断处理。

发送方向可概括为 SW-C → RTE → COM → PduR → CanIf → Can Driver → CAN Controller；接收方向反向逐层上送。具体链路取决于 PDU 类型、配置和通信栈模块，诊断报文通常还涉及 CanTp、Dcm 等模块。

~~~~mermaid
flowchart LR
  A[SW-C] --> B[RTE]
  B --> C[COM]
  C --> D[PduR]
  D --> E[CanIf]
  E --> F[Can Driver]
  F --> G[CAN Controller]
  G --> H[CAN Bus]
~~~~

### Q8. 为什么需要 PduR？COM 直接调用 CanIf 不行吗？

**答案：** PduR（PDU Router）将上层 PDU 使用者与底层通信接口解耦。若 COM 直接依赖 CanIf，那么 COM 就需要知道具体总线接口；加入 LIN、FlexRay、以太网、诊断或网关路由时，模块耦合和接口数量会快速增加。

PduR 的主要价值：

- 通过配置定义 PDU 的源与目的地。
- 支持不同上层模块复用统一路由服务。
- 在配置允许时支持一对多转发和网关路径。
- 把路由策略从业务代码中抽离，便于变更和验证。

**注意：** PduR 不负责 Signal 的打包/解包；那是 COM 等上层模块的职责。PduR 处理的是 PDU 级别的路由。

## 四、非易失存储

### Q9. NvM 模块是什么？它和掉电保存有什么关系？

**答案：** NvM（NVRAM Manager）为上层提供按 NvM Block 管理非易失数据的服务。上层通过 NvM API 请求读写，不必直接操作底层 Flash/EEPROM 的擦写细节。

典型数据包括学习值、配置参数、故障相关数据和需要掉电保留的状态。NvM 常与 MemIf、Fee/Ea、Fls/Eep 等模块配合：

- NvM：管理逻辑数据块、请求队列、校验与恢复策略。
- MemIf：在上层存储管理与底层存储设备抽象之间提供统一接口。
- Fee：在 Flash 上模拟 EEPROM 行为（若项目采用 Fee）。
- Ea：在 EEPROM 上提供 EEPROM 抽象（若项目采用 Ea）。
- Fls / Eep：执行具体 Flash / EEPROM 设备访问。

**重要边界：** NvM 不等于“掉电瞬间自动保存所有 RAM”。项目必须设计写入触发策略、关机时间预算、写入优先级、冗余/CRC 配置和恢复策略。

### Q10. 为什么 NvM 通常不直接写 Flash，而要通过 Fee？

**答案：** Flash 擦除粒度通常大于逻辑数据块，且擦写寿命有限；上层却希望以小块数据为单位更新。Fee 在采用 Flash 仿真 EEPROM 的架构中负责把逻辑块读写映射为底层 Flash 操作。

Fee 常见职责包括：

- 管理逻辑块到 Flash 位置的映射。
- 通过追加写、有效性标记等机制避免简单覆盖。
- 在设计允许时进行磨损均衡和垃圾回收。
- 在启动恢复时识别有效数据记录。

~~~~mermaid
flowchart TB
  APP[SW-C / Dcm 等上层模块]
  NVM[NvM：逻辑 Block 管理]
  MEM[MemIf：统一存储接口]
  FEE[Fee：Flash EEPROM 仿真]
  FLS[Fls：Flash 驱动]
  FLASH[片上 / 外部 Flash]
  APP --> NVM --> MEM --> FEE --> FLS --> FLASH
~~~~

**注意：** Fee 并非所有项目必选。若使用 EEPROM，可能采用 Ea + Eep 路径；具体模块组合以 ECU 配置和所用 AUTOSAR 版本为准。Flash 的擦写寿命、扇区布局、掉电一致性保证也受芯片与 Fee 实现约束，不能仅凭“Fee 存在”就假定绝对不会丢数据。

## 五、工程验证清单

- 检查 ARXML 中 SW-C Port、Interface、Connector 与 ECU 部署是否一致。
- 对照 RTE 生成文件，确认 Rte_Read/Write/Call 的映射和 Runnable 事件。
- 对照 PDU 配置逐层核验 COM、PduR、CanIf、Can Driver 的 Tx/Rx 路径。
- 检查 NvM Block、RAM Block、校验、冗余、写入触发和回调配置。
- 在掉电测试中覆盖写入前、写入中、写入后多个断电时刻，验证启动恢复结果。
- 记录工具版本、AUTOSAR Release、供应商扩展和芯片手册依据。
